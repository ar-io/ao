## Overview

The message tracking system captures output messages generated during process evaluation and stores them in process-specific SQLite databases. This enables:

1. **Message Discovery**: Track all output messages generated by a process
2. **Delivery Tracking**: Monitor which messages need to be delivered/cranked
3. **Re-cranking**: Identify messages that failed delivery and need to be re-sent

## Architecture

The system consists of three main components:

### 1. Process Messages Database (`process-messages-db.js`)

Creates and manages process-specific SQLite databases that store output message metadata.

**Schema:**
```sql
CREATE TABLE process_messages (
  nonce INTEGER NOT NULL,
  input_message_id TEXT NOT NULL,
  output_message_reference TEXT NOT NULL,
  output_message_target TEXT NOT NULL,
  output_message_action TEXT,
  output_message_index INTEGER NOT NULL,
  created_at INTEGER NOT NULL,
  PRIMARY KEY (nonce, output_message_index)
)
```

**Fields:**
- `nonce`: The ordinate/nonce of the input message that was evaluated
- `input_message_id`: The ID of the input message that triggered this evaluation
- `output_message_reference`: A unique hash reference for the output message
- `output_message_target`: The target process ID where the message should be sent
- `output_message_action`: The value of the "Action" tag (if present)
- `output_message_index`: The index of this message in the output Messages array
- `created_at`: Timestamp when the record was created

**Database Location:**
Each process gets its own SQLite file at:
```
./data/process-messages/{processId}.sqlite
```

### 2. Message Tracker (`message-tracker.js`)

The `MessageTracker` class handles the extraction and storage of output messages.

**Message Filtering:**
Only messages that meet BOTH criteria are tracked:
- Has a `Target` field (i.e., not a patch message)
- Has a `Reference` tag in the Tags array

**Key Methods:**
- `trackMessages(output, processId, nonce, inputMessageId)`: Extracts and stores messages from evaluation output
- `extractReferenceTag(tags)`: Extracts the "Reference" tag value from message tags
- `extractActionTag(tags)`: Extracts the "Action" tag value from message tags

### 3. Message Verifier (`message-verifier.js`, `message-verifier-db.js`)

The verification system checks if output messages have been published to Arweave.

**Verification Database Schema:**
```sql
CREATE TABLE verification_messages (
  nonce INTEGER NOT NULL,
  input_message_id TEXT NOT NULL,
  output_message_reference TEXT NOT NULL,
  output_message_target TEXT NOT NULL,
  output_message_action TEXT,
  output_message_index INTEGER NOT NULL,
  created_at INTEGER NOT NULL,
  discovered_message_id TEXT,        -- Set when found on Arweave
  last_discovery_attempt INTEGER,    -- Timestamp of last check
  PRIMARY KEY (nonce, output_message_index)
)
```

**Key Features:**
- Cursor-based sync from discovery DB (uses nonce)
- Prioritizes never-attempted rows, then by nonce order
- Configurable retry delay (default 10 minutes)
- GraphQL queries to Arweave gateway
- Exponential backoff for rate limiting (up to 5 minutes)

### 4. Integration Point (`effects/worker/evaluator/index.js`)

The message tracker is integrated into the evaluation pipeline alongside the existing `eventVacuum` system. It runs after each successful evaluation (non-dry-run) and captures the output messages.

**Note:** The message tracker uses `realDateNow` (captured at module load) instead of `Date.now()` because AoLoader overwrites `Date.now()` for deterministic WASM evaluation.

## Configuration

### Environment Variables

Enable message tracking by setting:

```bash
# Enable message tracking
MESSAGE_TRACKING_ENABLED=true

# Optional: Specify custom database directory (default: ./data/process-messages)
MESSAGE_TRACKING_DB_DIR=/path/to/custom/db/directory
```

```bash
# Message Tracking Configuration
MESSAGE_TRACKING_ENABLED=true

# Other CU configuration...
```

## Usage

### Starting the CU with Message Tracking

1. Set the environment variables in your `.env` file or export them:
   ```bash
   export MESSAGE_TRACKING_ENABLED=true
   ```

2. Start the CU normally:
   ```bash
   npm start
   ```

3. As processes are evaluated, output messages will be automatically tracked in their respective databases

### Querying Tracked Messages

You can query the SQLite databases directly to inspect tracked messages:

```bash
# Open a process-specific database
sqlite3 ./data/process-messages/{processId}.sqlite

# Query all messages for a specific nonce
SELECT * FROM process_messages WHERE nonce = 123;

# Query messages by target
SELECT * FROM process_messages WHERE output_message_target = 'target-process-id';

# Query messages with a specific Action
SELECT * FROM process_messages WHERE output_message_action = 'Transfer';

# Get message count per nonce
SELECT nonce, COUNT(*) as message_count
FROM process_messages
GROUP BY nonce
ORDER BY nonce;
```

### Example Queries

**Find all output messages from a specific input:**
```sql
SELECT * FROM process_messages
WHERE input_message_id = 'some-message-id'
ORDER BY output_message_index;
```

**Find messages sent to a specific target:**
```sql
SELECT nonce, input_message_id, output_message_action, output_message_index
FROM process_messages
WHERE output_message_target = 'target-process-id'
ORDER BY nonce, output_message_index;
```

**Get statistics by Action type:**
```sql
SELECT
  output_message_action,
  COUNT(*) as count,
  MIN(nonce) as first_nonce,
  MAX(nonce) as last_nonce
FROM process_messages
GROUP BY output_message_action
ORDER BY count DESC;
```

## Message Verification

The verification system checks if output messages have been published to Arweave by querying the GraphQL gateway.

### Running the Verifier

```bash
# Run one verification cycle
node scripts/run-verifier.js qNvAoz0TgcH7DMg8BCVn8jF32QH5L6T29VjHxhHqqGE --once

# Run continuously (default 1 minute cycles)
node scripts/run-verifier.js qNvAoz0TgcH7DMg8BCVn8jF32QH5L6T29VjHxhHqqGE

# Check stats only
node scripts/run-verifier.js qNvAoz0TgcH7DMg8BCVn8jF32QH5L6T29VjHxhHqqGE --stats

# Custom options
node scripts/run-verifier.js qNvAoz0TgcH7DMg8BCVn8jF32QH5L6T29VjHxhHqqGE \
  --retry-after 5 \
  --batch-size 50 \
  --interval 30000
```

### Verifier Options

- `--discovery-dir <path>`: Discovery DB directory (default: ./data/process-messages)
- `--verification-dir <path>`: Verification DB directory (default: ./data/verification)
- `--graphql-url <url>`: GraphQL endpoint (default: https://arweave-search.goldsky.com/graphql)
- `--retry-after <minutes>`: Minutes before retrying unfound messages (default: 10)
- `--batch-size <n>`: Messages to verify per cycle (default: 100)
- `--interval <ms>`: Milliseconds between cycles (default: 60000)
- `--once`: Run one cycle and exit
- `--stats`: Show stats and exit

### How Verification Works

1. **Sync**: Pull new messages from discovery DB using nonce as cursor
2. **Queue**: Get pending messages (prioritize never-attempted, then by nonce)
3. **Query**: For each message, query Arweave GraphQL by Reference tag
4. **Update**: Set `discovered_message_id` if found, update `last_discovery_attempt`

### GraphQL Query

The verifier queries Arweave with:
- `Reference` tag matching the output_message_reference
- `Data-Protocol` = "ao"
- `From-Process` = the process ID
- `owners` = known MU wallet addresses

### Retry Logic

- Exponential backoff for rate limiting (429) and server errors (502, 503, 504)
- Initial delay: 1 second, doubles each retry, caps at 5 minutes
- Max retries: 5 (then process exits)

## Performance Considerations

- **Database per Process**: Each process has its own SQLite file, preventing lock contention
- **Transaction Batching**: Multiple messages are inserted in a single transaction
- **WAL Mode**: SQLite is configured with WAL (Write-Ahead Logging) for better concurrency
- **Automatic Checkpointing**: WAL files are automatically checkpointed when they exceed 100MB
- **Connection Pooling**: Database connections are cached and reused per process

## Debugging

### Enable Debug Logging

The message tracker uses the logger from the CU context. To see tracking logs, ensure your logger is configured to show debug level messages.

### Common Issues

**1. Database files not created**
- Check that `MESSAGE_TRACKING_ENABLED=true` is set
- Verify the base directory exists and is writable
- Check file permissions on the `data/process-messages` directory

**2. Messages not being tracked**
- Verify the message is not a dry-run (Read-Only)
- Check that `output.Messages` is present and non-empty
- Look for error messages in the CU logs

**3. Database locked errors**
- SQLite is configured with WAL mode to reduce locking
- Ensure you're not trying to write to the database from multiple processes simultaneously
- Check that checkpoint intervals are working correctly

## Integration with Existing Systems

This system integrates cleanly alongside the existing `eventVacuum` system:

```javascript
// Event vacuum processes log events
if (eventVacuum) {
  await eventVacuum.processLogs(...)
}

// Message tracker captures output messages
if (messageTracker) {
  await messageTracker.trackMessages(...)
}
```

Both systems are:
- Optional (enabled via environment variables)
- Non-blocking (errors don't fail the evaluation)
- Independent (can be enabled/disabled separately)

## Schema Evolution

If you need to modify the schema in the future:

1. Update the `createProcessMessagesTable` function in `process-messages-db.js`
2. Add a migration function to alter existing databases
3. Update the `insertMessage` method to include new fields
4. Update the documentation

Example migration:
```javascript
const migrateToV2 = (db) => {
  db.prepare(`
    ALTER TABLE process_messages
    ADD COLUMN delivery_status TEXT DEFAULT 'pending'
  `).run()
}
```
